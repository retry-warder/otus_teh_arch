# Подсистема «ТО»: план тестирования

07.11.2026 · Евгений Дубина

## 1. Цель и критерии приёмки

Цель — подтвердить в базе, что поставка `cf_fix` работает целиком: планирование и наряды ТО, замеры APDEX, обмен через RabbitMQ. Особое внимание — исправлениям Б1–Б8 из «Заключения по замечаниям»: до сих пор они проверены только чтением кода.

| В объёме | Вне объёма |
| --- | --- |
| подсистемы ТО, ОП, RMQ; складская заявка в базе-потребителе; права ролей; нагрузка на парке до 1000 ТС | прочие подсистемы демо-конфигурации; отказоустойчивость самого брокера |

**Критерии приёмки**

- Синтаксический контроль без ошибок.
- YAxUnit: все 107 тестов проходят; после прогона в базе нет объектов «ЮТ …».
- Vanessa Automation: все 7 фич (20 сценариев) проходят.
- Ручные сценарии обмена, APDEX и прав (раздел 3) дают ожидаемый результат.
- Формирование нарядов на 1000 ТС укладывается в целевое время операции (T = 30 с), APDEX операции не ниже 0,85.
- В журнале регистрации нет ошибок подсистем, кроме вызванных негативными сценариями.

Дефект по любому пункту Б1–Б8 или потеря/дубль складской заявки блокирует приёмку. Отклонения в оформлении и текстах сообщений — замечания, не блокеры.

## 2. Стенд и подготовка

| Элемент | Что нужно |
| --- | --- |
| Платформа | 1С:Предприятие 8.3.27, клиент-серверный вариант (нужны регламентные задания и фоновые потоки отправки) |
| База-источник | тестовая копия демо-конфигурации с поставкой `cf_fix`, расширение `YAXUNIT` с модулями из `tests.zip` |
| База-потребитель | копия базы-источника (те же справочники и UUID), для сценариев приёма заявок |
| Брокер | RabbitMQ с веб-консолью (management), доступный с сервера 1С; отдельный vhost для тестов |
| Инструменты | YAxUnit 25.12, Vanessa Automation с фичами из `features`, обработка «ТО: заполнение тестового парка», SMTP-заглушка для рассылки |

**Перед началом**

1. Скопировать `cf\` из `cf_fix.zip` поверх выгрузки, загрузить конфигурацию из файлов и обновить БД.
2. Удалить расширение `ОбменRMQ`, если оно ещё есть в базе.
3. Создать пользователей с ролями (для проверки прав):
    - `Администратор` — типовая роль;
    - `Диспетчер` — роль `ТО`;
    - `Аналитик` — роль `ОП_ОценкаПроизводительности`;
    - `АдминистраторОбмена` — роль `RMQ_АдминистраторОбмена`;
    - `Регламент` — роли `RMQ_АдминистраторОбмена` и `ТО`, от его имени выполняются регламентные задания.
4. Сделать копию базы до тестов (точка отката) и копию для базы-потребителя.
5. В тестовой базе оставить константу `RMQ_ИспользоватьОбмен` выключенной на этапах 3.1–3.3: иначе тесты проведения оставят записи в «Исходящих сообщениях».

## 3. Этапы тестирования

Этапы идут по порядку: следующий начинается, когда предыдущий без блокирующих дефектов.

### 3.1. Сборка и синтаксис

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| С-1 | Загрузить конфигурацию из файлов, обновить БД | без ошибок, без реструктуризации с потерей данных |
| С-2 | Конфигурация → Проверить модули (сервер, тонкий клиент, внешнее соединение) | ошибок нет в `RMQ_Получение`, `RMQ_Отправка`, `RMQ_ОбменПолныеПрава` и остальных модулях |
| С-3 | Открыть свойства заданий `RMQ_ОтправкаСообщений`, `RMQ_ПолучениеСообщений` | имя метода — `RMQ_Отправка.ОтправкаСообщений` и `RMQ_Получение.ПолучениеСообщений` (Б2) |
| С-4 | Открыть состав подсистемы «ТО» | есть `ТО_Интеграция` (Б7) |

### 3.2. Юнит- и интеграционные тесты YAxUnit

Запуск: `1cv8 ENTERPRISE … /C "RunUnitTests=<репозиторий>\tools\JSON\yaxunit.json"` или Сервис → YAxUnit с фильтром по тегам `ТО`, `ОП`, `RMQ`. Отчёт JUnit пишется в build/reports/yaxunit и в репозиторий не попадает; его приложить к протоколу.

| ID | Что проверяется | Ожидаемый результат |
| --- | --- | --- |
| Ю-1 | Полный прогон, 20 модулей | 107 из 107 успешно |
| Ю-2 | `ТестЗамерЗаписываетсяВнеТранзакции` (Б8) | создана ключевая операция, записан один замер |
| Ю-3 | `ТестУспешныйПриёмПишетЗамер` (Б1) | сообщение «Загружено», заявка создана, есть успешный замер «СозданиеСкладскойЗаявки» |
| Ю-4 | `ТестИдентификаторПоСодержимому` (Б4) | идентификатор детерминирован, 36 символов, разный для другого тела и очереди |
| Ю-5 | Данные после прогона | нет объектов «ЮТ …», нет замеров операций «ЮТ…», константа `ОП_ОтключитьЗамеры` в исходном значении |

При падении теста сначала сверить текст исключения и имена методов движка 25.12.

### 3.4. Обмен через RabbitMQ (вручную)

Подготовка: в источнике — подключение, топология из «Консоли RMQ» (`to.events` → `sklad.zayavki`, ключ `naryad.created`), обмен включён; в потребителе — подписка `sklad.zayavki` → «ТО.СкладскаяЗаявка». Задания идут от пользователя `Регламент`.

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| R-1 | «Проверить подключение» в карточке подключения | соединение установлено; в форме видна заглушка вместо пароля |
| R-2 | Провести наряд с видом ТО, у которого есть материалы | в «Исходящих» одно сообщение «Новое» с телом `naryad.created` |
| R-3 | Перепровести тот же наряд | новое сообщение не регистрируется |
| R-4 | Дождаться задания отправки (до 60 с) | статус «Отправлено», заполнена дата отправки; в очереди `sklad.zayavki` сообщение с `message-id` = `eventId` |
| R-5 | Дождаться задания получения в потребителе | во «Входящих» «Загружено», создана складская заявка с источником «RabbitMQ»; в регистре замеров успешный замер «СозданиеСкладскойЗаявки» (Б1) |
| R-6 | Из веб-консоли RabbitMQ опубликовать в `sklad.zayavki` то же сообщение с тем же `message-id` | новое входящее не записано, второй заявки нет |
| R-7 | Опубликовать то же тело дважды без `message-id` | первое записано с идентификатором-хешем (формат УИД), второе отброшено; заявка одна (Б4) |
| R-8 | Опубликовать сообщение с неверным JSON | входящее в статусе «Ошибка» с текстом, запись в журнале; остальные сообщения пакета обработаны |
| R-9 | Остановить RabbitMQ, провести наряд, дождаться двух запусков задания | сообщение не потеряно: «Ошибка», растёт число попыток; проведение наряда прошло без ошибки |
| R-10 | Запустить RabbitMQ | при следующем запуске задания — «Отправлено», порядок сообщений по наряду сохранён (Б5) |
| R-11 | Выключить `RMQ_ИспользоватьОбмен`, провести наряд | исходящее не регистрируется, задания ничего не делают |
| R-12 | После нескольких циклов заданий открыть в веб-консоли список соединений | число соединений от 1С не растёт от цикла к циклу (Б6) |

### 3.5. Права доступа

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| П-1 | `Диспетчер`: провести наряд, сформировать план | успешно; исходящее и замер записаны, хотя прав на объекты RMQ и ОП у роли нет |
| П-2 | `Диспетчер`: открыть подключения RMQ, отчёт APDEX | недостаточно прав |
| П-3 | `Аналитик`: отчёт APDEX, правка целевого времени | успешно |
| П-4 | `АдминистраторОбмена`: настроить подключение, задать пароль; запросом прочитать `RMQ_ПаролиПодключений` | настройка и смена пароля работают; чтение регистра — недостаточно прав |
| П-5 | `Администратор`: прочитать регистр паролей | чтение доступно — принятое ограничение (Б3), дефектом не считается |
| П-6 | У пользователя `Регламент` временно снять роль `ТО`, отправить сообщение в потребитель | входящее «Ошибка» с текстом о правах: задание больше не работает в привилегированном режиме (Б2). Вернуть роль, переобработать |

### 3.6. Замеры APDEX

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| А-1 | Выполнить по одному разу шесть ключевых операций: формирование, рассылка, проведение наряда и учёта наработки из формы, расчёт плана, создание заявки | по каждой операции есть замер с весом; элементы «Ключевых операций» созданы с целевым временем |
| А-2 | Вызвать сбой расчёта или создания заявки (например, чужой наряд в событии) | замер с комментарием «Ошибка: …» |
| А-3 | Отчёт «APDEX ключевых операций» за сегодня | по каждой операции N, S, T, F и APDEX = (S + T/2) / N сходятся с ручным пересчётом; в детальных строках 1 / 0,5 / 0 |
| А-4 | Установить `ОП_ОтключитьЗамеры` = Истина, повторить формирование | новых замеров нет, формирование работает |
| А-5 | В справочнике задать T = 0 и дубль имени операции | оба раза запись отклонена с понятным сообщением |

### 3.7. Нагрузка

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| Н-1 | Обработкой «ТО: заполнение тестового парка» создать 1000 ТС с историей показаний | парк создан без ошибок |
| Н-2 | Три раза запустить формирование нарядов и расчёт «Плана ТО» по всему парку | формирование не дольше 30 с; повторные запуски не создают дублей |
| Н-3 | С включённым обменом сформировать наряды по парку (сотни сообщений) | все сообщения отправлены за несколько циклов; в потребителе столько же заявок, сколько нарядов с материалами |
| Н-4 | Отчёт APDEX после Н-2 и Н-3 | APDEX формирования и создания заявок — не ниже 0,85; секунды на единицу объёма записать в протокол |

Не проверяется на стенде: сбой записи статуса после успешной публикации или обработки (ветки предупреждений в Б1 и Б5). Их не вызвать без искусственной ошибки в коде, поэтому они проверены чтением кода.
